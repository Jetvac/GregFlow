[English](DATA.md) · **Русский**

Файлы `data/datasets/*` (снимок рецептов и иконок) и `data/lang/ru_RU/` (перевод) **не хранятся в
репозитории**: планировщик скачивает их при первом запуске (окно «⚙ Настройка») и сверяет SHA-256.

- Источник: <https://github.com/ShadowTheAge/gtnh-data/tree/6d35153688de5ae8e02807b942099618de1d9276>
- Ветка `2.8.0-v5`, коммит `6d35153688de5ae8e02807b942099618de1d9276` («Data format v5 includes metadata», 2025-10-16)
- `data.bin`: git blob `b1d2a893b744f94a74b0e481a210c9aa4ae92374`,

- `atlas.webp`: git blob `375b307c70f1199910170e4eac7c87d25eda8dfd`,
  SHA-256 `fa05550ce9657ce49d4512b4aab7fe76d684b70745b0bc7b744c9ae0d6eb6ef5` (8192×5344, 32 px, 256 столбцов)
- Формат: бинарный формат 5 (gzip, little-endian int32). 41 091 предмет, 1 542 жидкости, 625 записей

- Все значения совпадают с записью `gtnh-2.8.0` в манифесте gtnhnei. Сервер при запуске сверяет

Повторно скачать и проверить: `python planner.py --fetch-data`.

## Что хранится для каждого рецепта

Из экспорта (ничего не дополняется догадками; отсутствующие поля = «нет данных»):

- стабильный ID рецепта (`r~…`), набор данных, имя карты рецептов (машины), список машин-крафтеров;
- входы/выходы: тип (предмет / жидкость / словарь руд), стабильный ID (`i:mod:name:meta[:nbt-hash]`,
  `f:mod:name`, `o:oreName`), количество за цикл, вероятность выхода;
- нерасходуемые входы — в экспорте GT они имеют количество 0 (программные схемы, формы, линзы);
- длительность в тиках, напряжение и сила тока (EU/t = V × A), уровень, `specialValue`,
  метаданные (например `coil_heat` для EBF), число конфликтов схем;
- для словаря руд — все допустимые варианты; в узле выбирается конкретный.

Связи создаются только при совпадении стабильного ID. Одинаковое название не считается совместимостью.

Узел машины хранит **снимок** рецепта внутри файла проекта (вместе с набором и SHA-256),
поэтому обновление каталога не меняет уже построенную линию. «Сравнить с каталогом» показывает отличия.

## Как получить настоящие данные 2.8.4

1. Собрать [ShadowTheAge/nesql-exporter](https://github.com/ShadowTheAge/nesql-exporter) и выполнить
   экспорт в **клиенте** 2.8.4 (с теми же модами и конфигами, что и на сервере; инструкция репозитория
   требует убрать BugTorch).
2. Обработать экспорт: `dotnet run <папка nesql>` из `ShadowTheAge/gtnh/export` → `data.bin` (+ `atlas.webp`).
3. В планировщике: «Данные» → «Выбрать data.bin…», затем «+ атлас». Набор получит пометку
   «не проверено» и собственный SHA-256; при активации каталог переключается целиком.

Адаптер читает форматы **5 и 7** (формат 7 — текущий выход экспортёра). Формат 7 проверен на
реальном экспорте `gtnh-data@2.9.0-v7` (SHA-256 `624c9a20…`, git blob `4e15fde3…`;
50 811 предметов, 1 476 жидкостей, 221 760 рецептов): тест `Format7Adapter` с переменной
`GTNH_TEST_FORMAT7`. Этот файл в планировщик не встроен.

Точечные правки без полного экспорта — через «Свои рецепты»: копия рецепта каталога сохраняет
источник (`dataset`, `recipeId`, SHA-256 набора, дату), ручной рецепт помечается `manual`.
Файл обмена: `gtnh-planner-recipes` v1 (JSON, кнопки «Импорт файла» / «Экспорт»).

## Русские названия

Экспорт рецептов содержит только английские названия и `unlocalizedName`. Русские названия
собираются из двух источников (`server/lang.py`), более поздний перекрывает ранний — как в игре:

| Источник | Что даёт | Как получен |
|---|---|---|
| `ru_RU.lang` внутри jar модов установки | переводы модов (≈120 jar) | только чтение `mods/*.jar` |
| [GTNewHorizons/GTNH-Translations](https://github.com/GTNewHorizons/GTNH-Translations), папка `ru_RU` | `GregTech_ru_RU.lang` (материалы `Material.*`), `config/txloader/load|forceload/*/lang/ru_RU.lang` (шаблоны `gt.oreprefix.*`, машины, моды) | `python planner.py --fetch-lang` или кнопка в «Данные»: файлы скачиваются на зафиксированном коммите в `data/lang/ru_RU/`, в `manifest.json` записаны коммит, git blob и SHA-256 каждого файла; при несовпадении SHA-256 перевод не используется |
| `GregTech.lang` установки | английские шаблоны (`gt.metaitem.01.2018.name=%material Dust`) и английские имена материалов | только чтение |

Название предмета-материала GregTech строится как в игре: английский шаблон из `GregTech.lang` →
ключ `gt.oreprefix.material_dust` → русский шаблон `[Пыль] %s` + перевод материала `Material.magnesium`
= «[Пыль] Магний». Если какой-то части нет, русское название не придумывается — показывается
английское. Покрытие на 2.8.0: 36 604 из 42 633 ресурсов, 123 карты рецептов. Не переведены:
ванильные предметы Minecraft (их `ru_RU.lang` есть только в клиенте игры) и материалы, которых нет в переводе.
Индекс кешируется в `data/lang/names-<набор>-ru.json` (пересобирается при изменении источников).

## Энергия: кабели, генераторы, топливо

- **Кабели и провода** — из `gregtech-*.jar` установки (только чтение): байткод
  `gregtech/loaders/preload/LoaderMetaPipeEntities.class` разбирается (не исполняется), из цепочек
  `WireCableBuilder` берутся материал, уровень напряжения, ампераж провода 1x, потери на блок
  изолированного кабеля (`lossCable`) и голого провода (`lossWire`). Результат с именем jar и SHA-256
  кешируется в `data/energy/cables.json`. Для 2.8.4 (gregtech 5.09.51.482): 57 материалов, например
  олово — LV, 1 А, потери 1 (кабель) / 2 (провод) EU на блок. Размер (1x…16x) и иконки — из экспорта.
- **Генераторы** — предметы GregTech, у которых в подсказке экспорта есть «Voltage OUT» и которые
  являются машинами карты топлива либо указывают «Fuel Efficiency» / расход пара (45 штук).
  Напряжение и КПД — из подсказки. Ампераж на выходе не указан в данных; по умолчанию 1 А
  (одноблочные генераторы GT), его можно изменить.
- **Топливо** — карты рецептов с `fuel_value` в метаданных. Для жидкостей (и капсул с жидкостью)
  `fuel_value` трактуется как EU за 1 L (правило GT для жидкого топлива), итог × КПД генератора.
  Для твёрдого топлива (наквадах и т.п.) смысл `fuel_value` зависит от генератора — значение
  не подставляется, его нужно ввести вручную. Паровые турбины: расход пара из подсказки
  («Consumes up to 1552L of Steam per second» при 32 В → EU за литр, КПД уже учтён).
- **Модель потерь**: каждый ампер теряет `потери на блок × длина` EU, машина получает
  `V − потери·длина` на ампер; генератор отдаёт `нужно × V / Vd`.
- **Распределение** — по запросу, как в сети GT. Каждая машина запрашивает EU/t, которые взяла бы при
  текущей загрузке по сырью; генератор покрывает все запросы в пределах мощности и топлива, и только
  настоящая нехватка делится пропорционально запросам. Вход ⚡ блока — бюджет EU/t, который машины
  внутри делят так же, поэтому объединение в блок не меняет цифр. Не моделируются: трансформаторы,
  аккумуляторы/буферы, многоамперный приём машин, переменный КПД турбин-мультиблоков.
